## 1. Диспетчер сессий ИИ-агентов

**Зачем:** видеть в одном месте, что происходит с несколькими агентами, и не переключаться между вкладками для проверки.

Примеры: «Muse ждёт ответа», «Codex завершил задачу», «Сборка упала». Эти статусы показываются только при наличии достоверного события.

- [ ] Добавить общий список сессий с привязкой к проекту, вкладке и панели.
- [ ] Показывать состояния: работает, завершено, ошибка, требуется внимание, состояние неизвестно.
- [ ] Добавить переход из списка непосредственно в нужную сессию.
- [ ] Добавить системные уведомления с переходом в соответствующую вкладку/панель.
- [ ] Учесть существующие настройки уведомлений и защиту от повторов и частых событий.
- [ ] Выбрать первый поддерживаемый CLI-агент после проверки доступных событий или механизма интеграции; реализовать адаптер к нему.

**Границы:** запуск и завершение команды оболочки не равны началу и окончанию задачи внутри интерактивного агента. Для ожидания ответа или подтверждения нужны события самого агента. Молчание терминала и его заголовок не являются достаточными признаками. При отсутствии интеграции показывать «неизвестно», не угадывать.

**Критерии готовности:**

- [ ] Поддерживаемый агент сообщает о завершении и запросе внимания; интерфейс отображает именно эти события.
- [ ] Нажатие на уведомление открывает правильную сессию, в том числе в разделённой вкладке.
- [ ] Восстановление окна и повторное получение события не создают дублирующие уведомления.
- [ ] Неподдерживаемые агенты продолжают работать как обычные CLI-программы.

## 2. Запуск всего проекта одним действием

**Зачем:** открывать готовое окружение проекта, а не вручную создавать несколько терминалов при каждом начале работы.

Пример: PowerShell в репозитории, Ubuntu в WSL, сервер разработки, панель тестов и отдельная сессия агента.

- [ ] Добавить сохраняемое рабочее пространство проекта, объединяющее несколько профилей запуска.
- [ ] Сохранять оболочки, дистрибутивы WSL, рабочие папки, вкладки, панели и их пропорции.
- [ ] Разрешить явное указание стартовых команд для отдельных сессий.
- [ ] Добавить запуск рабочего пространства из интерфейса и палитры команд.
- [ ] При повторном открытии подключаться к ещё работающим сессиям, не запускать их команды заново.
- [ ] Предусмотреть просмотр и подтверждение команд при импорте чужого рабочего пространства.

**Границы:** это набор сессий для проекта поверх существующих профилей и раскладок. Открытие папки само по себе не должно выполнять команды из файлов проекта. Повторный щелчок и восстановление окна не должны дублировать серверы, тесты и агентов. После перезагрузки запуск задач должен быть явным действием пользователя.

**Критерии готовности:**

- [ ] Один запуск создаёт ожидаемый набор сессий с правильными папками и раскладкой.
- [ ] Повторное открытие окна сохраняет связь с живыми процессами без повторного выполнения команд.
- [ ] Недоступная оболочка, папка или WSL-дистрибутив дают понятную ошибку для соответствующей сессии.
- [ ] Импортированное описание не выполняет команды без предварительного согласия пользователя.

## 3. История команд с результатами

**Зачем:** находить конкретный запуск, его вывод и ошибку без поиска по всему содержимому терминала.

Пример: найти последнюю неудачную сборку, скопировать только ошибку или вернуть команду в строку ввода для редактирования.

- [ ] Ввести надёжные события начала и окончания команд оболочки; начать с PowerShell 5.1 и 7.
- [ ] Сохранять отдельные записи запусков: команда, папка/проект, время, длительность, код завершения и вывод.
- [ ] Добавить общую локальную историю с фильтрами по проекту, сессии и результату выполнения.
- [ ] Добавить копирование команды отдельно от вывода и доступного текста ошибки.
- [ ] Разрешить повторное использование команды через вставку для редактирования, без автоматического выполнения.
- [ ] Добавить настройку хранения истории, очистку, ограничение срока/объёма и исключение приватных сессий.
- [ ] Расширить интеграцию на выбранные оболочки WSL после проверки их протоколов событий.

**Границы:** не определять границы команд только по виду приглашения или тексту вывода. Полноэкранные TUI-приложения и неподдерживаемые оболочки остаются обычным терминалом. Не выдавать произвольно выделенные строки за достоверный stderr или внутренние команды агента. История локальная; её содержимое не отправляется ИИ или в облако автоматически.

**Критерии готовности:**

- [ ] Успешная, ошибочная и прерванная команда получают корректный результат либо явно обозначенное неизвестное состояние.
- [ ] Многострочные команды, кириллица и управляющие последовательности не ломают отображение и копирование.
- [ ] Длительный вывод не блокирует ввод и переключение вкладок.
- [ ] Отключённая история и приватные сессии не сохраняют новые записи; очистка удаляет выбранные данные.
- [ ] Возврат команды из истории не запускает её без действия пользователя.

## 4. Отдельная ветка и рабочая папка каждому агенту

**Зачем:** дать нескольким агентам параллельно менять один проект, не перезаписывая рабочие файлы друг друга.

Уточнение: каждому агенту действительно нужна своя ветка. Но в одной рабочей папке Git одновременно выбрана только одна ветка, поэтому одной смены ветки недостаточно. Для параллельной работы использовать `git worktree`: один репозиторий, отдельные ветки и отдельные рабочие папки.

Пример:

| Сессия | Ветка | Рабочая папка |
| --- | --- | --- |
| Агент интерфейса | `feature/design` | отдельный worktree для интерфейса |
| Агент исправления вставки | `fix/paste` | отдельный worktree для вставки |

- [ ] Добавить создание сессии агента с собственной веткой и worktree от выбранной исходной ветки.
- [ ] Показывать связь «агент — задача — ветка — папка» в интерфейсе.
- [ ] Проверять занятые имена веток, существующие папки и уже используемые worktree.
- [ ] Добавить просмотр изменённых файлов и diff перед принятием результата.
- [ ] Предусмотреть явное принятие результата через merge или перенос выбранных коммитов; не объединять работу автоматически.
- [ ] Добавить отдельное действие завершения/очистки worktree с проверкой несохранённой работы и подтверждением.

**Границы:** worktree разделяет рабочие файлы, но не является песочницей безопасности. Процессы, порты, зависимости вне папки и часть состояния Git могут оставаться общими. Не сбрасывать и не удалять пользовательские изменения. Не удалять ветку или папку автоматически при закрытии вкладки. Конфликты объединения требуют отдельного решения пользователя.

**Критерии готовности:**

- [ ] Два агента работают в разных папках и ветках; изменения файлов одного не меняют рабочие файлы другого.
- [ ] Пользователь может просмотреть результат каждого агента до объединения.
- [ ] Объединение и удаление происходят только по явному действию пользователя; незакоммиченная работа защищена от потери.
- [ ] Для обычной работы с одним агентом создание worktree не становится обязательным.

## 5. Встроенная диагностика «Почему команда не работает?»

**Зачем:** объяснять типовые проблемы окружения, например почему `codex` находится в Windows Terminal, но не находится в текущей сессии TerminalV.

**Кто выполняет диагностику:** сам TerminalV, обычным программным кодом и понятными правилами. ИИ, подписка и отправка данных внешнему сервису не нужны.

- [ ] Добавить запуск диагностики по запросу пользователя с указанием имени команды.
- [ ] Проверять доступность исполняемого файла и путь его разрешения в выбранном окружении.
- [ ] Учитывать оболочку, Windows/WSL и выбранный дистрибутив.
- [ ] Сравнивать относящиеся к проблеме значения PATH там, где доступны достоверные данные о текущей сессии и актуальном окружении.
- [ ] Объяснять ограниченный набор подтверждённых причин: команда не найдена, устаревшее окружение сессии, установка только в другой среде.
- [ ] Показывать факты проверки, степень определённости и безопасные следующие действия.
- [ ] Версию программы показывать только когда её можно определить безопасно без запуска диагностируемой команды.

**Границы:** это не универсальный ИИ-ремонтник. Если фактическое окружение работающей вкладки неизвестно, нельзя объявлять точную причину только по окружению хоста или реестру. Результат в таком случае — «недостаточно данных» с объяснением.

Проверки только читают данные: не запускать диагностируемую программу, не устанавливать пакеты, не менять PATH и настройки, не вводить команды в занятую сессию. Исправления — отдельное действие с явным согласием пользователя. Не сохранять и не передавать полный набор переменных окружения или секреты.

**Критерии готовности:**

- [ ] Диагностика различает подтверждённое отсутствие команды, устаревшее окружение и несовпадение Windows/WSL.
- [ ] При нехватке сведений показывает неизвестный результат, а не выдуманную причину.
- [ ] Проверка не исполняет пользовательскую команду и не меняет систему или ввод активного терминала.
- [ ] Отчёт содержит только относящиеся к проблеме безопасные сведения.

## Основа и предлагаемый порядок реализации

1. Начать с надёжных событий начала и окончания команд оболочки — основы пункта 3 и обычных уведомлений о завершении. Текущая передача рабочей папки и BEL не заменяют такую интеграцию.
2. Реализовать историю команд из пункта 3 поверх этих событий.
3. Добавить рабочие пространства проектов из пункта 2.
4. Добавить диспетчер из пункта 1 и первый проверенный адаптер агента. Состояния интерактивного агента требуют отдельной интеграции, даже если события оболочки уже работают.
5. Реализовать ветки/worktree из пункта 4 после базового управления проектами и сессиями.

Пункт 5 — диагностику окружения — можно делать независимо отдельной задачей. Начать с небольшого набора доказуемых причин, расширять по реальным случаям.
