# План первой публикации TerminalV в RuStore

Дата: 25 сентября 2026 года. Статус: план, реализация и публикация не запускались.

Цель: подготовить подписанный Android APK TerminalV.Mobile, проверить его на устройстве и отправить на модерацию RuStore. Исходное предположение — бесплатная версия без встроенных покупок. Первую загрузку выполнить вручную через консоль RuStore; автоматизацию загрузки можно добавить после первого выпуска.

Оценка: 3–5 рабочих дней подготовки при отсутствии крупных дефектов; до недели с исправлениями. Регистрация аккаунта, ожидание материалов владельца и модерация в эту оценку не входят. Предыдущая оценка 2–4 дня уточнена после обнаружения хранения секретов в Preferences.

## Что уже есть

- MAUI-проект `src/TerminalV.Mobile/TerminalV.Mobile.csproj`: Android, ApplicationId `com.terminalv.mobile`, версия `1.1.2`, ApplicationVersion `8`.
- Прямой SSH, шлюз TerminalV и встроенный Tailscale, мобильный интерфейс и иконка.
- Скрипты сборки `tsnet.aar` в `tools/tsnet-bridge/` и проверки APK `scripts/verify-mobile-apk.ps1`.
- Тесты мобильного моста и SSH. Наличие тестов не означает, что текущий релиз проверен.
- Существующий `.github/workflows/release.yml` выпускает Windows-пакеты; отдельного Android release workflow при просмотре не обнаружено.

Рабочая папка содержит незакоммиченные изменения, включая мобильный клиент. Перед сборкой кандидата нужно зафиксировать согласованный состав релиза и его commit SHA, сохранив остальные изменения пользователя.

## 1. Зафиксировать параметры выпуска — 0,25 дня

- [ ] Сохранить `com.terminalv.mobile`, если это идентификатор уже распространявшихся APK; проверить сертификат подписи прежнего APK.
- [ ] Найти существующий релизный keystore и определить владельца резервной копии. Если выпусков с постоянным ключом ещё не было, подготовить постоянный ключ; не заменять существующий вслепую.
- [ ] Выбрать ApplicationVersion выше всех ранее распространявшихся версий и соответствующую отображаемую версию.
- [ ] Зафиксировать заявленные функции первой версии: прямой SSH, подключение к шлюзу и Tailscale — только после их проверки. Не обещать локальную Windows-оболочку на телефоне.
- [ ] Владелец регистрирует или предоставляет доступ к аккаунту разработчика RuStore и определяет публичный email поддержки.

Готово, когда известны commit кандидата, идентификатор, версия, ключ подписи и владелец аккаунта. Если подпись прежнего APK отличается, заранее определить последствия для обновления уже установленных копий.

## 2. Подготовить клиент к публичному выпуску — 0,75–1,25 дня

- [ ] Перенести пароль SSH, gateway token и Tailscale auth key из `Preferences` в `SecureStorage`; проверить все места чтения и записи в `Home.razor` и `MobileBridge.cs`.
- [ ] Добавить миграцию существующих значений: удалять старое значение только после успешного сохранения в защищённом хранилище; при ошибке показывать понятный запрос повторного входа.
- [ ] Удалить рабочие адреса и пароль по умолчанию из первого запуска. Показывать пустую форму подключения с примерами, которые не запускают соединение автоматически.
- [ ] Проверить Android backup: сейчас в манифесте `allowBackup=true`. Настроить исключение секретов и состояния авторизации из резервных копий; проверить также экспорт настроек внутри приложения.
- [ ] Проверить, что диагностические сообщения и экспорт не раскрывают пароли и токены.
- [ ] Добавить доступную ссылку на сведения о конфиденциальности и контакт поддержки.
- [ ] Сопоставить разрешения итогового APK с реальными функциями, включая разрешения, добавленные зависимостями.

Готово, когда миграция и повторный вход работают, первый запуск не использует чужие реквизиты, а резервные копии и логи проверены на секреты. Точечные проверки миграции выполнить в CI.

## 3. Настроить воспроизводимую Android-сборку — 0,75–1 дня

- [ ] Добавить отдельный workflow с ручным запуском, не меняя процесс Windows-релизов.
- [ ] На CI установить согласованные версии .NET 10/MAUI, Node.js, Go, JDK, Android SDK/NDK и gomobile/gobind. Зафиксировать версии инструментов вместо получения `latest` во время релиза.
- [ ] В чистом checkout собрать `tsnet.aar`, затем UI и Release APK для выбранных архитектур. Исходная конфигурация проверки — ARM64 и x86_64.
- [ ] Подписать APK постоянным ключом из защищённых CI secrets; исключить ключ и пароли из логов и артефактов. Резервную копию ключа хранит владелец отдельно от CI.
- [ ] Выполнить `scripts/verify-mobile-apk.ps1`: актуальность UI, наличие `tsnet.Tsnet_` и нативных библиотек.
- [ ] Проверить сертификат, ApplicationId, versionCode, min/target SDK, отсутствие debuggable-флага, состав разрешений, выравнивание APK и совместимость нативных библиотек с 16-КБ страницами.
- [ ] Сохранить APK, SHA-256 и отчёт проверки с commit SHA как артефакты CI.

Готово, когда чистая сборка выдаёт проверенный подписанный APK. Сборку, publish и тяжёлые тесты выполнять в GitHub Actions либо на Xeon; на RE-7LQD67AHCM0R — только редактирование и лёгкие проверки.

## 4. Проверить релизный APK — 0,75–1,25 дня

- [ ] В CI запустить релевантные `TerminalV.Mobile.Tests`, `TerminalV.Ssh.Tests` и тесты мобильного интерфейса. Для обнаруженных дефектов добавить адресные регрессионные проверки.
- [ ] На физическом Android-телефоне проверить чистую установку, первый запуск и отсутствие сети.
- [ ] Проверить прямой SSH, заявленные методы входа, неверные реквизиты, таймаут и повторное подключение.
- [ ] Проверить шлюз TerminalV и Tailscale: вход, выбор ПК, подключение, выход и повторный вход.
- [ ] Проверить кириллицу, вставку, Enter, Backspace, Ctrl+C, прокрутку, вкладки и изменение размеров при показе клавиатуры.
- [ ] Проверить возврат из фона, блокировку экрана и смену Wi-Fi/мобильной сети: нет зависаний, потеря соединения понятна, восстановление доступно.
- [ ] Проверить обновление поверх прежнего APK с тем же сертификатом: настройки и миграция секретов сохраняют работоспособность.
- [ ] На CI-эмуляторе или другом устройстве дополнить проверку для актуального Android и 16-КБ страниц. Если заявленная минимальная версия не проверена, зафиксировать этот пробел и решить его до заявления полной совместимости.

Готово, когда к конкретному SHA-256 APK приложен краткий протокол устройств, версий Android, сценариев и результатов, без блокирующих дефектов.

## 5. Подготовить карточку и доступ для модерации — 0,5 дня

- [ ] Написать русское краткое и полное описание с ясным назначением: удалённый терминал; для подключения нужен SSH-сервер или ПК с настроенным шлюзом.
- [ ] Подготовить иконку и реальные скриншоты релизной версии без личных серверов, реквизитов и содержимого рабочих сессий.
- [ ] Выбрать категорию и возрастную маркировку по фактическим функциям; заполнить контакты и описание версии.
- [ ] Опубликовать сведения о конфиденциальности на постоянном доступном URL: локально хранимые данные, SSH-подключения, использование Tailscale, удаление данных и контакты. Проверить фактические потоки данных, не заявлять отсутствие передачи данных без проверки.
- [ ] Подготовить изолированный тестовый SSH-сервер с ограниченной учётной записью и инструкцию для проверяющего. Для остальных заявленных режимов описать проверяемый сценарий и предоставить необходимые тестовые условия без доступа к рабочему tailnet.
- [ ] Проверить лицензии распространяемых зависимостей и наличие необходимых уведомлений об авторских правах.

Готово, когда карточка соответствует доступным функциям, ссылки открываются, а проверяющий может пройти сценарий подключения.

## 6. Загрузить и пройти модерацию

- [ ] Перед отправкой повторно сверить актуальные требования консоли RuStore.
- [ ] Передать владельцу готовый комплект: APK с контрольной суммой, результаты проверки, тексты, изображения, URL конфиденциальности и инструкцию для модерации.
- [ ] После решения владельца о публикации загрузить именно проверенный APK и заполнить карточку. Выбрать ручную публикацию после одобрения, если такой порядок нужен владельцу.
- [ ] Отправить на модерацию, обработать конкретные замечания; при изменении бинарного файла увеличить versionCode и повторить затронутые проверки.
- [ ] После публикации проверить установку из RuStore и базовое подключение. Зафиксировать опубликованную версию, сертификат, SHA-256 и ссылку на карточку.

Готово, когда приложение доступно в RuStore и установленная из магазина версия проходит базовый сценарий. Срок и результат модерации заранее не гарантируются.

## Участие владельца и порядок работ

От владельца нужны аккаунт RuStore, публичные контакты, сведения о прежнем ключе подписи, доступ к телефону для проверки и решение о выпуске готового кандидата. Секреты передавать через защищённые механизмы, не включать в этот документ.

Порядок: параметры выпуска → исправления хранения данных → сборка в CI → проверка APK → загрузка и модерация. Подготовку аккаунта, карточки и тестового сервера можно вести во время технической подготовки.

Главные причины увеличения срока: неизвестная подпись прежних APK, проблемы чистой сборки AAR/MAUI, дефекты на устройстве и недоступность тестовой среды для модерации.
